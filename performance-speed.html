Performance Optimization

Page Speed

Most speed problems are really weight problems — less to download, less to run.

On this page

  1. Reducing request count
  2. Caching and caching basics
  3. JavaScript's real cost
  4. Fonts without the flash

Reducing request count

"Every additional request carries connection overhead—each file the browser has to fetch adds time, even before it downloads. The more requests, the slower the page starts to feel. Reducing that count is one of the most reliable ways to speed things up.

Bundle assets sensibly, rely on HTTP/2 (or HTTP/3) multiplexing to handle multiple files efficiently, and inline truly critical CSS to avoid extra round trips. These all reduce the number of trips a browser needs before it can render anything useful. Fewer requests, faster paint."

Caching and caching basics

"Proper cache headers mean a returning visitor doesn't re-download assets that haven't changed—saving time and bandwidth. A CDN serves static files from a location physically closer to the visitor, cutting latency even further. Together, they make repeat visits noticeably faster.

Static hosting platforms like Vercel and Netlify handle most of this automatically—caching, CDN distribution, and asset optimization are built right in. That's part of why they suit a static site like this one. Less configuration, more speed, out of the box.

JavaScript's real cost

"A script's download size isn't its real cost—parsing, compiling, and executing it on the main thread often costs more than the download itself. The browser has to process every byte of JavaScript before it can run, and that processing takes time and CPU power. Big bundles mean big delays.

Splitting code so a page only loads what it actually needs—rather than one giant bundle for the whole site—keeps that cost proportional to what a given page uses. Load only what's necessary for that specific page, and the browser does less work. Faster load, snappier interactions, happier visitors."

Fonts without the flash

"A poorly loaded web font causes a visible flash of unstyled or invisible text—readers see either a jarring style shift or nothing at all while they wait. Either way, it hurts trust and makes the page feel broken.

font-display: swap shows fallback text immediately while the custom font loads. Preloading the critical font file gives it priority so it arrives sooner. And subsetting to only the characters your site actually uses shrinks the file size. Together, they cut the visual penalty and keep text readable from the first moment."

Weight is the root cause

Before reaching for a specific fix, ask what's actually heavy on the page — bytes downloaded and main-thread time explain most speed problems better than any individual technique.

Action checklist

  • ✓Audit total page weight, not just load time on one connection
  • ✓Confirm cache headers are set correctly for static assets
  • ✓Code-split JavaScript so pages only load what they use
  • ✓Set font-display: swap and preload critical font files
  • ✓Re-check weight after adding any third-party script
